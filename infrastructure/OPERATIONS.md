# Operating this infrastructure

Written 2026-08-21, after a day in which roughly fifteen separate faults
surfaced. Almost none of them were introduced that day. They were *collected*
that day, because it was the first time in months that anything actually ran.

The through-line is one sentence:

> **Configuration that describes a system nobody verified exists.**

Every rule below is here because it was paid for. The evidence is kept
attached to the rule, because a rule without its incident gets deleted by the
next person who finds it inconvenient.

---

## 1. Declared is not running

Check the running system, not the file that claims to configure it.

| declared | actually running |
|---|---|
| `smtpd_client_auth_rate_limit = 10` in `main.cf` | `0` — unlimited, since Dec 2025 |
| `DUCKDB_PATH` set in the container env | read by nothing; hardcoded `./analytics.db` |
| `RATE_LIMIT_PER_MINUTE` / `_HOUR` in config | read by nothing |
| branch protection requiring `✅ CI Success` | no workflow emitted that check |

The postfix image was built by hand on 2025-12-09 and never rebuilt, so every
`main.cf` edit committed after that date was inert. The file said one thing;
`postconf -h` said another for eight months.

**Rule:** before claiming a config change is in effect, query the running
process. `postconf -h <param>`, `docker inspect`, `psql -c 'SHOW …'`,
`curl` the endpoint. Not the file. Not the PR.

---

## 2. A failing cron is silent, and monitoring that watches itself is not monitoring

`/opt/liberation-platform/backup.sh` was in the crontab. It never existed.
**597 failures** between 2025-10-24 and 2026-08-21, writing `not found` into a
log nobody read. The entry was duplicated, so it failed twice nightly.

`enhanced-monitoring.sh` — same directory, also absent, running every two
minutes. Roughly **216,000 failures** over the same ten months. The thing whose
job was to notice the backup failing was broken in exactly the same way.

**Rules:**
- Alerting must not depend on the same file, host, or path as the thing it
  watches. The backup freshness check is an *inline cron line with no script
  file*, deliberately — a checker in a file can vanish the way `backup.sh` did.
- Alert on *transition into* failure with a repeat cap. A check running every
  five minutes that mails on every failure sends 288 identical messages a day
  and trains you to filter them: the same outcome as no alerting.
- Absence of alerts is not evidence of health unless something proves the
  alerter is alive.

---

## 3. An unrestored backup is a hypothesis. So is an untriggered rollback.

Nothing on this server had ever been backed up, and nobody knew.

Rollbacks written the same day, and what happened when they fired:

| mechanism | outcome |
|---|---|
| Caddy deploy rollback | **reverted a correct config**, twice — the new config was fine, the service was wedged |
| postfix deploy rollback | **could not run** — `set -euo pipefail` aborted the script before reaching it |
| analytics build-before-swap (#10) | **held** — failed build, production never stopped |

**Rules:**
- Restore the backup into a scratch database and count rows. `pg_restore
  --list` proves readability; only a restore proves content.
- Prune old images/backups **only after** verification succeeds. Deleting the
  rollback target on success is what left a later failure with nothing to
  return to.
- A rollback path that has never executed is untested code on the most
  dangerous path in the system.

---

## 4. Fixes that live only on the box will be destroyed, or will block the next deploy

Four instances in one day:

- the postfix image, hand-built and never rebuilt
- DKIM keys, generated by hand (survived only because the volume outlived the container)
- a `docker-compose.yml` healthcheck fix, correct and uncommitted — it later
  blocked a deploy with `Your local changes would be overwritten by merge`
- a `Dockerfile` edit made to restore service, which blocked the same deploy

**Rule:** when you fix something on the server to restore service, that is
step one of two. Step two is committing it. An uncommitted server-side fix is
a landmine with a delay fuse — either the next deploy destroys it, or it stops
the next deploy for reasons unrelated to what is being deployed.

---

## 5. Build before you swap

The analytics deploy stopped and removed the running container, then built.
The build failed (Dockerfile pinned Go 1.21.6 against a `go.mod` requiring
1.24) and the previous image had already been pruned by the prior run. Nothing
running, nothing to return to. **Eight minutes down for a fault that was
detectable before anything was touched.**

**Rule:** build → record the running image by ID → swap → health-check →
*then* prune. A failed build must be a no-op.

---

## 6. Config for a name that does not resolve is not inert

`www.analytics` and `www.staging` had Caddy vhosts and no DNS records, from
the day they were written. Caddy attempts ACME for every named site on load;
NXDOMAIN sends certmagic into a 300-second retry; systemd's reload timeout
fires mid-retry and kills the reload — **which severed the deploying SSH
session (exit 255), so the rollback never ran.**

They were harmless for months, then took the site down during an unrelated
change.

**Rule:** the Caddy deploy now resolves every vhost before touching anything
and refuses if any is missing. Add the DNS record first, or don't add the
block.

---

## 7. Validation can have side effects

`caddy validate` opens its log writers. Run under `sudo`, it **creates** any
missing log file owned by `root`. Caddy runs as `caddy` and then cannot open
its own log, so the reload fails with `permission denied` — long after the
validate that caused it appeared to succeed.

This blocked the listmonk vhost for an hour, and the error naming the cause
was visible in the first failed attempt and dismissed as noise.

**Rules:**
- Pre-create every log file as `caddy:caddy` before validating or reloading.
- Read the error text. The cause was in the first log and cost an hour because
  it was skimmed.

---

## 8. Names must match reality

Production analytics runs as `liberation-analytics`. The workflow called it
`liberation-analytics-production` and then separately ran `docker rm
liberation-analytics` on **every** deploy — including staging ones. That
single line was simultaneously how the deploy appeared to work and how a
staging deploy took production down.

**Rule:** when a workflow needs a hardcoded exception to function, the
exception is hiding a mismatch. Fix the mismatch.

---

## 9. Shared state defeats environment separation

The staging analytics container mounts **the same DuckDB file** as production.
DuckDB permits a single writer, so staging locked production out of its own
database and put it into a restart loop.

A different container name and a different port are not isolation when both
point at the same file.

**Rule:** either give staging its own data path and database, or delete the
concept. Currently it costs nothing to keep and can cost an outage.

---

## 10. Manual deploy gates control timing, not correctness

Every outage on 2026-08-21 happened during a deliberate, manually dispatched
deploy. Hand-gating means nothing ships by surprise. It says nothing about
whether what ships works.

**Rule:** the gate is not the safety mechanism. Build-before-swap, preflight
checks, and health-checked swaps are.

---

## 11. Deferred cleanup does not run on `os.Exit`

`main()` ended in `log.Fatal(http.ListenAndServe(...))`. `log.Fatal` calls
`os.Exit`, and **`os.Exit` does not run deferred functions** — so `defer
server.Close()` at the top of `main` had never executed. Not once in nine
months. Nothing handled SIGTERM either, so `docker stop` returned in 0.287s.

DuckDB folds its write-ahead log into the database file on clean close.
Without one, every row lived only in the log: a **12KB** database file beside a
**15MB** WAL. A backup of the `.db` alone would have restored nothing.

**Rule:** a service holding a database must handle SIGTERM, shut down the
listener, and close the database explicitly. Verify by stopping it and
watching the file sizes change.

---

## 12. Test the leg that is failing

A test that mailed successfully from inside the postfix container was reported
as end-to-end proof. It bypassed listmonk entirely — the exact hop that was
broken. It proved relay, DKIM and DMARC, and nothing about the failure being
investigated.

**Rule:** name which hops a test covers before calling it end-to-end. If the
test would still pass with the broken component removed, it is not testing it.

---

## 13. Report state you have read, not state you remember

Several wrong claims came from reciting merge status and PR numbers from
memory rather than re-reading them. A `gh pr merge` that printed
`To use administrator privileges … add --admin` did nothing, and the deploy
that followed shipped `main` without the change.

**Rule:** no completion claim without a check that would have failed if the
thing were broken. Not "I merged it" — `gh pr view` says `MERGED`. Not "it
deployed" — the container's image ID changed.

on the root disk** despite their names. The backup script refuses to run if its
destination resolves to the same block device as `/`, for exactly this reason.
